ofelia: optional admin API + UI plan v1

Scoped from mcuadros/ofelia. For review before any code is written.

Problem & prior art

Ofelia has no runtime introspection and no way to fire a job outside its cron schedule. This is a known, long-standing gap in the upstream project (#58 "web ui", #198 "Manually run job", #101 "No purty UI?") — open since 2018/2019, no PRs ever attempted, and a maintainer confirmed "Ofelia has no UI unfortunately." Several commenters explicitly said a read-only history view would already satisfy them. This is open ground, not a competing effort.

Decision: in-binary optional feature, not a sidecar

Ofelia already has a clean precedent for optional subsystems that are off by default:

  • middlewares.NewSave/NewSlack/NewMail — each returns nil (no-op) if its config struct is empty. Always called, inert unless configured.
  • DockerHandler label-watching — a real background goroutine, only started with the --docker CLI flag on DaemonCommand.

We follow the same shape for the admin API/UI: a new optional subsystem, present in the same binary/image, dormant unless explicitly configured.

Default behavior is unchanged. No new port is opened, no new goroutine starts, unless the user sets api-addr (INI) or passes --api-addr (flag). Zero new attack surface for existing deployments.

Shape of the change

1. New api package

cli/
  daemon.go        (+ a few lines: construct + start API if configured)
  config.go        (+ ApiConfig struct, same squash pattern as SlackConfig/SaveConfig)
api/                (new package)
  server.go         net/http server, JSON handlers
  history.go        in-memory ring buffer of recent Executions per job
  static/           embedded UI (go:embed), ultra-minimal HTML/CSS/JS, no build step

2. Config (same opt-in pattern as Slack/Save/Mail)

[global]
api-addr = :8081           ; empty/absent = disabled (default)
api-history-size = 200     ; max executions kept in memory, per job (default 200)

Equivalent CLI flags on daemon: --api-addr, --api-history-size — mirrors the existing --docker/--docker-filter flag style.

v1 explicitly excludes: auth (trusted/internal network only for now), persistence across restarts (history is in-memory, cleared on restart — same lifetime as the process today), and bulk/tag-based "run all" (deferred, per #198 commenters' own v2 suggestion).

3. History: make the dead field real

core/job.go already declares history []*Execution on BareJob — currently unused, nothing appends to it. Plan: append each *Execution in jobWrapper.stop() (core/scheduler.go), capped ring buffer, per job, default 200 executions (configurable via api-history-size), no disk persistence in v1. Per-job (not a global total) so a noisy @every 1m job can't evict history for a daily/weekly job — at 200/job that's ~3.3h of scrollback for a 1-minute job, 8+ days for hourly, ~200 days for daily, which covers "did it run / did it fail recently" without unbounded memory growth from large stdout/stderr buffers (circbuf cap is already 10MB/stream per core/common.go). If durable history is wanted later, back it with the existing Save middleware's on-disk JSON dumps instead of inventing a new store.

4. Manual trigger

POST /api/jobs/{name}/run invokes the same path a cron fire takes — build an Execution + Context and call jobWrapper.Run() (or factor its body into a reusable RunNow(j Job) on Scheduler) outside of the cron ticker. No new execution logic — reuses the existing middleware chain (Overlap/Slack/Save/Mail all still apply).

5. API surface (v1, minimal)

MethodPathReturns
GET/api/jobsname, type, schedule, next run, last status, running?
GET/api/jobs/{name}job detail + last N executions (id, start, duration, exit status, stdout/stderr size)
GET/api/jobs/{name}/executions/{id}/lograw stdout/stderr for one run (from in-memory circbuf, same data already captured today)
POST/api/jobs/{name}/runtriggers immediately, returns the new execution id

No edit/delete/create endpoints in v1 — matches what #101/#58 commenters actually asked for ("read-only... would mean a world to me"), and avoids re-implementing config management as a second source of truth next to the INI/labels.

6. UI

Two screens only, as scoped. Server-rendered or a single embedded static HTML+fetch() page — no framework, no build step, no bundler; consistent with keeping ofelia a single small Go binary. Mockups below.

Build phases

  1. Core: wire up history ring buffer in core/scheduler.go; add Scheduler.RunNow(name string).
  2. API: new api package, JSON handlers over the above, config-gated start in cli/daemon.go.
  3. UI: single embedded HTML page (go:embed), vanilla JS fetch, the two screens above.
  4. Tests: handler tests (httptest, matching existing slack_test.go style), scheduler RunNow test.
  5. Docs: README section documenting api-addr/api-auth-token, off-by-default callout.
  6. Optional follow-up: propose upstream as a PR against #58/#198 once validated internally — resolves both with an opt-in, minimal-surface design that matches what maintainers/commenters said they'd actually accept.

v1 scope — decided

  • No auth — trusted/internal network only for now.
  • No persistence across restarts — in-memory history only, same process lifetime as everything else today.
  • No bulk run — single-job trigger only; bulk/tag-based "run all" deferred per #198 commenters' own v2 suggestion.
  • History cap: 200 executions, per job (not a global total) — a noisy @every 1m job can't evict history for a daily/weekly job. 200/job covers ~3.3h scrollback for minutely jobs, 8+ days for hourly, ~200 days for daily. Configurable via api-history-size if it needs to move later.
